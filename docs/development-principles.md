# AutoAdv 開発原則

## 製品から設計する

1. 製品の中心は、**LunaHookで本文を取得する、話者・本文・Voiceを設定して必要な台詞へTTSを適用する、音声の有無にかかわらず会話を進める**ことである。仕様と実行契約は利用者の操作・結果から決める。
2. 最初に完成時の処理順、状態の所有者、Domain間の契約、GUIと保存設定の関係を決める。クラス・旧テスト・既存設定を起点に目標を逆算しない。
3. 利用者の指示は、追加すべきラベル・状態・分岐を直接指定する実装仕様ではなく、達成すべき目的、制約、または露呈した問題を示す入力として扱う。実装前に指示を製品上の目的、失敗原因、成立すべき性質へ分解し、成果はその問題が関連する経路全体で解消されたことで判定する。指示文へ直接対応できることや失敗を説明できることだけを目的として、中間状態、説明ラベル、例外分岐、観測項目を追加しない。内部概念を増やす場合は、それ自体が製品挙動に必要で、責務と根拠を既存概念で代替できない場合に限る。
4. 調査や新しい判定手段の追加は、特定できた実用上の問題に対する効果と費用を基準に判断する。開発上の整理や計測だけを独立した製品価値としない。
5. ゲームごとのHOOK・音声・操作の違いは取得機能と作品別設定を活用して扱う。設計は実用的な会話処理を優先し、未知の事実を都合よく確定扱いしない。

## 再構築と再利用

6. ゼロベースとは完成時モデルを新たに決めることである。既存コードの評価や旧責務の全件解明を開始条件にせず、有用なLunaHook・Irodori・Utterance・音声・GUI資産は動作契約に照らして再利用する。
7. 同じ仕事をする複数の実行経路や設定正本を作らない。採用した実装は、取得から会話送りまで実際につながる形で組み込む。責務分割とコード削減は利用しやすさ・保守・性能のための手段である。
8. LunaHook上流のゲーム対応・ビルド資産・Python側機能を活用する。特にflush、選択スレッドの同期、複数選択出力の集約は上流が持つ意味と保証範囲を先に確認する。Lunaのflush通知をゲーム内台詞の完全な境界と断定したり、同種の独自文字列確定器を重ねたりしない。上流版と必要な権利表示を管理し、独自再実装の費用と継続更新負担を考慮する。
9. 利用者のゲーム・HOOK・Voice設定を一つの正本で保存・復元する。旧AutoAdv形式との互換経路をruntimeやPersistenceへ残さず、現行設定形式を唯一の製品契約とする。

## 観測・推論・操作

10. 外部系の値は、まずその取得元が実際に観測した事実として保持する。ASR token時刻、VAD、PCM供給、HOOK通知等を、取得した層で「再生中」「終了」「成功」「失敗」へ読み替えない。決定論的な正規化・照合も、何を対応付けたかを失わない測定として扱う。
11. 推論の純化は条件数を減らすことではなく、根拠と責務を保つことで行う。pure function化、boolean化、共通score化だけを責務分離とみなさない。複数の観測を状態へ写す場合は、どの観測から何を導いたかを追跡でき、観測されていない事実を否定形から補わない。
12. 操作判断は推論結果と利用者方針を組み合わせる一つの所有者に集約する。推論不能を成功へ変換するフォールバック等の利用者方針は、観測・推論の意味を書き換えず別理由として扱う。同じ責務の第二判定器や別入力経路を追加しない。

## 検証と公開

13. 不変原則・状態遷移・State所有・Domain間整合性・Application契約を優先して検証する。単体テストとモックは実ゲーム・実音声・GUIの統合動作の代用にしない。
14. 変更の受入れは、指示に対応するコード・状態・ログが存在することではなく、分解した製品上の問題が不変条件、状態遷移、統合挙動で解消されたことによって行う。説明用の状態や診断値が期待どおり出ることだけを成功条件にせず、問題を別の状態や経路へ移しただけでないことを確認する。
15. 不変原則は、個別ロジックや既知不具合の説明ではなく、広い入力または許可された状態遷移に対して実装方法によらず成立する製品上の性質として定義する。
16. 同じ原則の具体例をテストとして累積しない。可能な限りproperty、状態モデル、同値クラスへ統合し、既知不具合の再現ケースは独立した契約を表す場合だけ恒久化する。同じ契約を複数層で重複検証せず、それを十分に検証できる層で所有する。
17. clean install、OS差等ローカルで検証できない項目はGitHub CIで検証する。ローカル実行不能を理由に必要な検証を変更単位から除外しない。テスト失敗時は実装だけでなく、テスト契約が正準仕様と一致しているか確認する。
18. 実装変更時は既存のproperty・状態モデル・契約の更新を基本とし、変更や不具合ごとにテストを追加して実装履歴を固定化しない。既存テストは継承を前提にせず、テスト数や従来のアサーションを維持するために実装を変えない。private状態、固定call回数、fixture名、現在のアルゴリズム分割等を、製品上の不変条件でない限りテスト契約へ昇格させない。
19. テスト契約の監査によって実装上の歪みが露呈した場合、アサーションだけを緩めたり別のモックへ置き換えて終えない。製品目的、観測可能な事実、責務、実環境で成立すべき性質へ戻って実装側も再評価し、テスト都合で導入された状態、cache、閾値、近似経路、fixture依存を必要に応じて撤去または再設計する。
20. 修正後は、同じ原因が他の状態遷移・設定・音声・入力・GUIに残らないか確認する。代表箇所だけの修正で完了を宣言しない。
21. 責務がまとまり関係する検証を通過した単位でcommit・publishする。Fast CI成功とWindows実ゲーム成立は区別する。作業環境、branch、Publish Gateway、`main`とversionの制約は`docs/publish.md`に従う。
22. 実機検証の観測系は、fixtureが与えた刺激、製品が実際に受けた入力・生成した出力・行った操作という事後解析可能な事実を保存する。検証器自身が製品状態、成功・失敗原因、安全性を再推論する第二の状態機械を作らない。
