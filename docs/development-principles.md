# AutoAdv 開発原則

## 製品から設計する

1. 製品の中心は、**LunaHookで本文を取得する、話者・本文・Voiceを設定して必要な台詞へTTSを適用する、音声の有無にかかわらず会話を進める**ことである。仕様と実行契約は利用者の操作・結果から決める。
2. 最初に完成時の処理順、状態の所有者、Domain間の契約、GUIと保存設定の関係を決める。クラス・旧テスト・既存設定を起点に目標を逆算しない。
3. 調査や新しい判定手段の追加は、特定できた実用上の問題に対する効果と費用を基準に判断する。開発上の整理や計測だけを独立した製品価値としない。
4. ゲームごとのHOOK・音声・操作の違いは取得機能と作品別設定を活用して扱う。設計は実用的な会話処理を優先し、未知の事実を都合よく確定扱いしない。

## 再構築と再利用

5. ゼロベースとは完成時モデルを新たに決めることである。既存コードの評価や旧責務の全件解明を開始条件にせず、有用なLunaHook・Irodori・Utterance・音声・GUI資産は動作契約に照らして再利用する。
6. 同じ仕事をする複数の実行経路や設定正本を作らない。採用した実装は、取得から会話送りまで実際につながる形で組み込む。責務分割とコード削減は利用しやすさ・保守・性能のための手段である。
7. LunaHook上流のゲーム対応・ビルド資産・Python側機能を活用する。特にflush、選択スレッドの同期、複数選択出力の集約は上流が持つ意味と保証範囲を先に確認する。Lunaのflush通知をゲーム内台詞の完全な境界と断定したり、同種の独自文字列確定器を重ねたりしない。上流版と必要な権利表示を管理し、独自再実装の費用と継続更新負担を考慮する。
8. 利用者のゲーム・HOOK・Voice設定を一つの正本で保存・復元する。旧AutoAdv形式との互換経路をruntimeやPersistenceへ残さず、現行設定形式を唯一の製品契約とする。

## 観測・推論・操作

9. 外部系の値は、まずその取得元が実際に観測した事実として保持する。ASR token時刻、VAD、PCM供給、HOOK通知等を、取得した層で「再生中」「終了」「成功」「失敗」へ読み替えない。決定論的な正規化・照合も、何を対応付けたかを失わない測定として扱う。
10. 推論の純化は条件数を減らすことではなく、根拠と責務を保つことで行う。pure function化、boolean化、共通score化だけを責務分離とみなさない。複数の観測を状態へ写す場合は、どの観測から何を導いたかを追跡でき、観測されていない事実を否定形から補わない。
11. 操作判断は推論結果と利用者方針を組み合わせる一つの所有者に集約する。推論不能を成功へ変換するフォールバック等の利用者方針は、観測・推論の意味を書き換えず別理由として扱う。同じ責務の第二判定器や別入力経路を追加しない。

## 検証と公開

12. 不変条件・状態遷移・Domain間整合性・Application契約を検証する。単体テストとモックは実ゲーム・実音声・GUIの統合動作の代用にしない。
13. テスト体系は正準仕様の不変条件・状態遷移・Domain間整合性・Application契約から再構成する。既存テストは継承を前提にせず、同じ契約を直接検証する証拠として必要なものだけ採用する。実装クラス、helper、内部field、撤去済み経路の不存在、特定の委譲方法など実装履歴だけを固定するテストは置かない。テスト数や従来のアサーションを維持するために実装を変えない。
14. 修正後は、同じ原因が他の状態遷移・設定・音声・入力・GUIに残らないか確認する。代表箇所だけの修正で完了を宣言しない。
15. 責務がまとまり関係する検証を通過した単位でcommit・publishする。Fast CI成功とWindows実ゲーム成立は区別する。作業環境、branch、Publish Gateway、`main`とversionの制約は`docs/publish.md`に従う。
