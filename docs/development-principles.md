# AutoAdv 開発原則

## 製品から設計する

1. 製品の中心は、**LunaHookで本文を取得する、話者・本文・Voiceを設定して必要な台詞へTTSを適用する、音声の有無にかかわらず会話を進める**ことである。仕様と実行契約は利用者の操作・結果から決める。
2. 最初に完成時の処理順、状態の所有者、Domain間の契約、GUIと保存設定の関係を決める。クラス・旧テスト・既存設定を起点に目標を逆算しない。
3. 調査や新しい判定手段の追加は、特定できた実用上の問題に対する効果と費用を基準に判断する。開発上の整理や計測だけを独立した製品価値としない。
4. ゲームごとのHOOK・音声・操作の違いは取得機能と作品別設定を活用して扱う。設計は実用的な会話処理を優先し、未知の事実を都合よく確定扱いしない。

## 再構築と再利用

5. ゼロベースとは完成時モデルを新たに決めることである。既存コードの評価や旧責務の全件解明を開始条件にせず、有用なLunaHook・Irodori・Utterance・音声・GUI資産は動作契約に照らして再利用する。
6. 同じ仕事をする複数の実行経路や設定正本を作らない。採用した実装は、取得から会話送りまで実際につながる形で組み込む。責務分割とコード削減は利用しやすさ・保守・性能のための手段である。
7. LunaHook上流のゲーム対応・ビルド資産・Python側機能を活用する。特にflush、選択スレッドの同期、複数選択出力の集約は上流が持つ意味と保証範囲を先に確認する。Lunaのflush通知をゲーム内台詞の完全な境界と断定したり、同種の独自文字列確定器を重ねたりしない。上流版と必要な権利表示を管理し、独自再実装の費用と継続更新負担を考慮する。
8. 利用者のゲーム・HOOK・Voice設定を一つの正本で保存・復元する。既存設定の移行は原本保全と内容確認を優先する。

## 検証と公開

9. 不変条件・状態遷移・Domain間整合性・Application契約を検証する。単体テストとモックは実ゲーム・実音声・GUIの統合動作の代用にしない。
10. 旧テストは正準仕様との関係を一件ずつ確認し、役立つものを採用する。テスト数や従来のアサーションを維持するために実装を変えない。失敗時はテスト契約の必要性も評価する。
11. 修正後は、同じ原因が他の状態遷移・設定・音声・入力・GUIに残らないか確認する。代表箇所だけの修正で完了を宣言しない。
12. 責務がまとまり関係する検証を通過した単位でcommit・publishする。Fast CI成功とWindows実ゲーム成立は区別する。作業環境、branch、Publish Gateway、`main`とversionの制約は`docs/publish.md`に従う。
