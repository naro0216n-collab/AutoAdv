# AutoAdv — 完成時製品仕様

本書はAutoAdvを**ゼロベースで再設計した完成時契約**である。旧アーキテクチャ、過去の実装手順、現行テストから派生した要件を含めない。実装の移行手順は`rebuild-transition.md`に分離する。

## 1. 製品の目的と利用範囲

AutoAdvは個人利用のWindows GUIアプリとして、ゲームの台詞をLunaHookから取り込み、必要な台詞にIrodori TTSを割り当て、元のゲーム音声の有無を問わず会話を自動で進める。

利用者が達成したい結果は以下の三つである。

1. **本文を取得する**：LunaHookの多様なゲーム対応を活用し、作品ごとに適切なHOOKを発見・選択・保存・復元して、原文を継続的に得る。
2. **読み上げを補完する**：話者の識別、本文分離、読み替え、Voice割当て、TTS対象選択を設定できる。ゲームに原音がある台詞は原音を優先し、原音のない台詞や指定した台詞は適切なタイミングでIrodori TTSを使用する。
3. **会話を自動で送る**：既存音声がある場合は対応音声の再生終了、TTSを使う場合は実再生終了、いずれも使わない場合は閲覧時間を考慮し、明示許可の下で次の通常台詞へ進める。

日常運用で別途LunaTranslatorを起動し設定を二重管理することを求めない。複数作品・複数プロファイルを継続して使える。機能が存在することではなく、この一連の操作が実際のゲームで役立つことを完成条件とする。

## 2. 対象範囲と追加機能の判断

**中核**はHOOK本文取得、Utterance解釈、選択的TTS、既存音声との同期、会話の自動送りである。これに必要なゲーム識別、HOOK管理、設定保存、入力対象確認、手動停止、GUI、障害通知を一体として提供する。

ゲーム全体の状態認識、全ゲームに共通する選択肢の完全検出、選択肢の自動選択、汎用ゲーム操作エージェント、画面全域の解析、あらゆる場面の遷移証明は**完成要件ではない**。それらの実現や、不可能性の保証も要求しない。既存のHOOK情報等から選択肢や特殊な状態が分かる場合、取得した事実を会話進行の停止・補助に活用してよい。対象外の振舞いが副次的に可能でも、積極的な削除対象とせず、不成立を固定するテストを置かない。

新しい機能・観測・Adapterは、中核の実用上の問題と利用可能な根拠を示して必要性を判断する。稀な例外に備えるだけの汎用基盤や、状態を網羅する目的の追加を採用しない。作品差は、可能な限りHOOK選択・取得補正・Voice・待機・手動介入等の設定で吸収する。

## 3. 通常の利用体験とGUI

初期設定ではAutoAdvで既存のIrodori-TTS-Serverフォルダを指定し、必要な共通音声環境を設定する。以後はAutoAdvの起動時に、既存のサーバーが使えるか確認し、設定した既存環境から必要に応じて自動起動する。インストール、モデルダウンロード、音声素材の加工を勝手に始めない。利用可能なVoice IDを読み取り、GUIから試聴できる。

作品を登録または識別し、初回や取得不良時にHOOKを探索・選択して保存する。通常は作品・既定プロファイル・HOOK設定を復元し、毎回の再登録、PID手入力、別アプリでの操作、音声設定の重複入力を要求しない。作品識別が曖昧な場合はユーザーが選ぶ。ゲームをAutoAdvから起動する操作も利用できる。

ユーザーは本文と話者、適用中の読み・Voice、取得源と接続状態、音声の処理経路、進行の許可・停止理由を一つのGUIで確認できる。必要情報は無効時でも非表示にせず状態を示す。情報を隠して簡素化したり操作位置を不意に入れ替えたりしない。監視・TTS・入力の処理でGUIをブロックしない。

会話自動進行はユーザーが明示的に有効化・一時停止・再許可できる。音声の確認やHOOKの調整だけを行う場合はゲームへ入力しない。設定を変更した際は適用対象と反映タイミングを表示し、処理中の台詞へ無断で割り込ませない。

## 4. 本文取得とHOOK管理

標準の取得方式はLunaHookである。LunaTranslatorが持つ多様なゲームエンジン・エミュレーター対応、HOOK探索・手動追加・選択・保存・再接続・取得品質処理の実用機能を、上流への追随性も含めて利用する。ネイティブLunaHook/Hostと必要なビルド資産は一貫した上流版から取り込み、独自のゲーム別HOOKエンジンへ安易に置き換えない。Python側HOOK管理やGUI資産も、必要な機能に対して移植・統合・直接利用を比較し、手作業の再実装や上流変更追随の負担を抑える。

ゲームごとのHOOK候補と実際の原文を表示し、HOOKコード、取得元プロセス、スレッド/context等の識別情報、選択順、手動追加、取得補正、必要な複数HOOKの利用を扱う。複数HOOKが話者・本文・履歴等へ分かれる作品については、実際の取得特性に沿って解釈・組合せを設定できる。関係が確定できない複数出力を時刻だけで強引に一台詞へ結合しない。保存HOOKの復元は実際の候補との対応を確認し、曖昧なら再選択を促す。

受信結果には原文、取得源、ゲーム・プロファイル、実セッションと取得世代、HOOKの出自、受信順序、単調時刻、利用可能な取得状態を保持する。上流が復号・バッファ処理したテキストと、HOOKの真の生バイトを混同しない。本文の一通知が一台詞とは限らない。部分更新・空通知・重複・同文が連続する台詞・複数HOOKの混信を区別し、根拠が不十分なときに行境界や話者を創作しない。同文の別台詞も存在するため、本文の不一致を台詞境界の唯一条件にしない。

### 任意の代替取得

HOOKを使えない、または精度が低い作品では、ユーザーが明示的にOCRを選択できる。標準は既存のTesseract CLIを使う任意の取得Adapterで、作品別の範囲・エンジンパス・言語を保存する。自動インストールやHOOK障害時の無断切替、HOOKとOCRの二重取得・自動突合は標準動作にしない。OCRを使わない作品でOCRエンジンや画面領域の校正を要求しない。OCR結果は同じUtterance・TTS経路に渡すが、文字誤認やフレーム差分から確実な台詞境界を捏造しない。自動送りとの接続はその取得源で実用的な境界が確認できる範囲に限る。

## 5. Utteranceと作品別TTS設定

台詞について、観測原文、話者、本文、読み上げ用テキスト、音声照合用テキスト、適用ルールとVoiceを**一度解釈した同じUtterance**から導く。プレビュー、TTS、ASR、実行時表示で別々の再解析や別ルールを使わない。

作品・プロファイルごとに以下を調整できる。

- 話者名と本文の分離。引用符の有無、改行、区切り、発話者が別HOOKに現れる場合等に対応できる構造規則と優先順位。
- 通常の置換、正規表現、読み辞書、ルビの処理。特定人物名と複合語の読み分け、ルビの直前漢字を読み上げ文から除く処理等も規則として設定できる。
- 話者別Voiceと読み上げ対象の指定。原音を優先する話者、TTSで補う話者、読み上げない文章、未知話者の既定動作を設定できる。
- 表示・照合・読み上げに用いる文の差異と、適用される規則の確認・試聴。

一つの作品で音声がある人物とない人物が混在しても、原音を二重に読み上げず、未収録台詞を適切に補完できることを目指す。TTSサービスの選択、Voice ID、処理速度などの共通条件はグローバルに保持し、必要なものだけ作品側で上書きする。

## 6. 既存音声の照合・TTS・自動進行

本節が製品の中心的な実行契約である。

### 6.1 台詞ごとの処理

1. 選択取得源から本文候補と出自を受け取り、Utteranceを確定または更新する。候補の安定とゲーム画面全体の状態判定は同義ではない。
2. ゲームの対象音声をWindows Process Loopbackで取得し、VADと必要に応じた日本語ASRで**そのUtteranceに対応する原音**を照合する。BGM・効果音・他台詞の活動を、その台詞の音声開始・終了と同一視しない。
3. 対応する原音を確認した場合は原音優先で再生完了を待つ。TTS対象の台詞は設定と音声観測に従ってIrodoriを使用する。原音がない、または確認できない台詞は、作品の待機・TTSポリシーに従って補完する。**原音の不存在を完全に証明するためのゲーム全体監視は要求しない**。音声不明は音声なしという確定事実に読み替えず、利用者の選んだ補完ポリシーと制限を明示する。
4. 原音が遅れて確認できた場合は、進行中のTTSを適切に取消して原音へ譲る。TTSの場合は合成要求の完了ではなく実際の再生完了を判断する。読み上げなしを選んだ台詞は設定した閲覧時間を適用する。
5. 発話・閲覧が完了し、ユーザーの自動送り許可と対象入力条件が揃えば、その台詞に対応する送り操作を**一度だけ**行う。
6. 入力後は選択取得源から得られる新しい台詞の根拠を待ち、別台詞と判断できるときのみ次のUtteranceを処理する。部分更新、空通知、単なる時間経過、識別できない同文再通知を根拠に連打しない。進展の確認ができなければ停止して手動操作を可能にする。

原音の有無によって会話自動進行の操作体系を別にしない。一方、音声認識が曖昧、ASRが利用不能、ゲームが入力を受け付けていない、取得元が途切れた等の事態を成功扱いして連続入力することはない。TTSのみで使う作品がASRモデルや音声捕捉環境を必須設定しなければならない設計にもせず、明示的な利用モードで必要な依存だけを使う。

### 6.2 入力権限と停止

ゲームへの入力判断は一つの会話進行主体が所有する。取得Adapter、音声Adapter、TTS、GUIはそれぞれ観測・依頼・状態表示を担い、勝手に送りを発行しない。入力直前に対象ゲーム・ウィンドウ・フォーカス・セッション、手動介入、既存音声/TTSの活動、同一台詞への送信履歴を再確認する。ゲーム・プロファイル・HOOK・取得源・対象プロセスの切替、Host障害、停止操作では、旧候補・音声ジョブ・タイマー・入力許可を失効させる。遅配イベントで復帰させない。

ユーザーの明示許可は実際に原文を確認した後でも可能とし、行処理中であることだけを理由に許可操作が使えなくならない。停止と再開は通常操作であり、毎回プロファイルを作り直させない。手動介入は自動送りを停止し、再許可時に対象と現行台詞を改めて確認する。マウス移動などゲーム操作とは関係しない行動を安易に選択肢操作と誤認しない。

すべてのゲームの選択肢や特殊画面を認識することを要求しない。HOOK出力から確かに判断できる特殊情報があれば進行に利用できるが、選択肢の自動選択は完成条件ではない。判別できないゲーム固有の場面については誤動作の限界をUIで説明し、利用者が手動停止・操作できる。汎用的な画面状態判定、画面遷移ACK、選択肢不存在の証明を標準の入力ゲートには置かない。

## 7. ゲーム、設定、実行セッション

設定の正本はAutoAdvに一つだけ置く。

- **共通設定**：IrodoriフォルダとAPI、使用可能Voice、必要な音声捕捉/ASR環境、標準の待機・再生条件、保存先・ログ。
- **ゲーム情報**：表示名から独立した安定ID、実行ファイルや必要な識別子、既定プロファイル。ゲームの実行ファイルが共通・変更された場合や複数候補が一致した場合は、誤った自動確定をしない。
- **ゲーム内プロファイル**：取得方式、HOOK選択・手動コード・補正、本文解析規則、話者/Voice割当て、音声・送りの作品別設定。複製・改名・削除・既定設定・切替をGUIで行える。
- **実行セッション**：接続中のゲーム、取得元と接続世代、音声対象、入力対象、現在Utterance、発話処理、自動送り許可を一元的に管理する。PID/HWND等の起動ごとに変わる情報を永続プロファイルの正体として扱わない。

必要な作品ではHOOK、音声、ウィンドウ入力が別プロセスになることがあるため、実際の根拠に従って対象を結びつけられる。ただし**ゲーム内の全プロセスや画面状態を常時網羅的に観測する機能**は要求しない。識別ができない場合はユーザーによる選択を利用する。

## 8. 技術的境界と運用条件

LunaHook Native/Hostはプロセス外で管理し、ゲームへの入力・音声判断を担わせない。Hostからの出力と故障はセッションへ伝える。ゲームへの既存HOOK注入との競合、権限不足、保護機構等がある場合は勝手に上書き・終了・迂回せず理由を示す。外部ゲームや外部Lunaを無断停止しない。保護機構の回避を機能成立の条件としない。

Luna上流採用版と必要な依存を固定・記録し、x86/x64のビルド・ABI・実接続を確認して更新する。Nativeエンジン・Host・関連Pythonコードを異なるコミットから無秩序に混在させない。上流追随を支援する取り込み手順と改変履歴を保持するが、関連のないLuna製品機能を常設することは要求しない。

本製品は個人利用専用であり、配布用インストーラや商用運用の設計を完成条件としない。ただし公開リポジトリでLuna由来ソースを扱う場合のGPL等の適用、原著作者表示、対応ソース、第三者依存の権利は確認して遵守する。

## 9. 受入条件

実際の使用シナリオを満たすことを基準にする。

| 使用シナリオ | 完成の判断 |
|---|---|
| HOOKが取得できるゲームを初回設定 | AutoAdvだけで探索・本文プレビュー・選択・保存ができる |
| 登録済みゲームを再起動 | ゲーム識別と保存HOOK・話者/Voice設定が復元され、再登録を毎回求めない |
| 話者・本文が複雑なゲーム | 本文・読み・話者・Voiceが設定に従って一致し、必要な複数HOOKを使える |
| 原音のある台詞 | 対応する既存音声を優先し、その再生途中に送らない |
| 原音のない台詞 | 設定したVoiceのTTSまたは閲覧時間で処理し、ASRがない場合にも利用できる |
| 音声あり・なしが混在 | 原音とTTSの重複や早送りを抑え、台詞ごとに自動処理が継続する |
| 連続する通常会話 | 明示許可後、実際の入力対象へ適切なタイミングで送り、台詞を飛ばさない |
| 部分更新・同文反復・別HOOK混信 | 境界を捏造して連打しない。区別不能なら停止・手動再開ができる |
| 切替・切断・手動介入 | 古い音声・入力要求が新セッションで実行されない |
| HOOKが使えない作品 | OCRを明示選択でき、標準HOOK作品にOCR導入を要求しない |
| GUI | 接続・取得原文・適用Utterance・Voice・音声経路・許可/停止理由が実処理と一致する |

Unit/architecture/integrationテストでは入力一元化、取得元と世代、Utterance一貫性、音声とTTSの相互排他、実再生終了、重複入力抑止、設定復元を確認する。Windows CIでNativeのx86/x64ビルド、関連Adapter、GUI等を検証する。さらに、異なるゲームでHOOK受信・有声/無声混在・実入力・手動停止を確認し、未検証の部分は明示する。モックやテストで状態を直接作っただけで実ゲーム成立を宣言しない。

**非要件の不成立を検証項目にしない。** 選択肢自動選択や追加の補助機能が偶然実現できることは問題ではなく、それを妨げる実装やテストを作らない。検証は対象機能が実際に役立つことへ集中する。
