# AutoAdv — LunaHook広域移植・統合実装指示書

**対象**：`naro0216n-collab/AutoAdv`（通常開発は`develop`）
**策定日**：2026年10月20日
**採用案**：第2案「LunaHookとHOOK関連機能を広く移植し、AutoAdvに統合する」＋HOOK標準・OCR任意／進行証拠再設計
**利用形態**：個人利用専用のWindows GUIアプリ

## 1. 目的と完成条件

AutoAdvを、別途起動したLunaTranslatorへ操作を委ねない、単独で日常運用できる音声同期・自動進行アプリとする。LunaからはC++ネイティブHOOK資産だけでなく、ゲーム検出、HOOK探索・選択・復元、複数HOOK管理、取得品質向け処理、関連する設定・操作機能を広く取り込む。上流の改良を継続的に取り込める構成とし、同等機能の再実装や上流改修の手作業再現を減らす。

目標とする通常操作は、(1) AutoAdv起動、(2) 対象ゲームの起動、(3) 初回または取得失敗時のみHOOKの選択・補正、(4) 自動進行の明示的許可、である。既定プロファイルが適切な登録済みゲームに対して、毎回の設定確認・保存を義務づけない。AutoAdvから保存済みゲームを起動する操作も選択可能とし、ゲーム起動とプロファイル選択の重複を増やさない。登録済みゲームでは識別・プロファイル・保存HOOKが自動的に復元される。Irodori-TTS-Serverは既存仕様どおり、ルートフォルダを一度指定した後はAutoAdv起動時に必要に応じて自動起動する。LunaTranslatorの別途インストール、手動起動、個別のゲーム登録・HOOK選択を通常操作の必須条件にしない。

AutoAdvは一作品専用とせず、複数作品と一作品内の複数プロファイルを継続保存する。HOOKまたは明示選択OCRからの取得、本文解釈、Voice割当て、音声照合、必要時の画面観測、進行制御が一連の操作として成立することを完成条件とする。**取得成功、音声合成成功、監視開始のいずれもゲームへの自動入力許可を意味しない。**

「移植量を最小化する」「Luna側Pythonを必ず書き直す」「LunaのGUI資産を使用しない」「現行AutoAdvコードを温存する」という制約は設けない。選定基準は**完成後の利用価値、初期実装コスト、上流更新の取込みコスト、実動作と回帰検証のコスト**の総合である。逆に、既存Lunaの機能だからというだけで無関係な翻訳・OCR・TTS製品機能まで常設しない。

## 2. 正準仕様と変更の位置付け

作業開始時に必ず `docs/README.md`、`docs/development-principles.md`、`docs/integration-spec.md` を読む。今回の方針はユーザー指示による仕様変更であるため、コード変更に先立ち **`docs/integration-spec.md` を本指示書の完成時動作へ改訂し、`docs/README.md` の説明と矛盾を解消**する。現行仕様の「Luna公開WSへの一本化」「HOOK選択UIを移植しない」「原文とPID/HOOK情報が取得不能」等は、新しい取得方式に置換する。`docs/publish.md` に残る初回構築未成立などの現状と一致しない記述は、実際の標準経路を変更せず、確認済み運用事実に合わせて整理する。旧実装や既存テストへ新仕様を合わせるためにdocsを改変しない。

本指示書に明記のない、共有 `Utterance`、Irodori起動・Voice取得、選択的TTS、native Process Loopback＋VAD/ASR、根拠のあるゲーム入力可否の肯定的証拠（画像認識は任意）、選択肢手動操作からの復帰、単一Controller、入力前再検査、1行1入力以下、遷移ACK待ち等の完成条件は引き続き有効とする。旧仕様由来のテストについては保持を前提とせず、新しい契約に照らして再選定する。

## 3. 取り込むLuna資産と統合方針

移植元：`https://github.com/HIllya51/LunaTranslator`。調査時点の上流参照コミットは `51884b6c88cba8c42e98ce3e43c4f408017082a1`。実際の初回取込みでは採用コミットを固定・記録し、そのコミットに含まれる各ソースと依存関係を一貫して扱う。異なる上流リビジョンのHost・Hook・共通型・資源を混在させない。

| 対象 | 方針 | 主な目的 |
|---|---|---|
| `src/NativeImpl/LunaHook/LunaHook` | **エンジン別ソース・エミュレーター対応・resourceを含め広く取得** | 既存のx86/x64ゲーム対応を保持し、新規対応を追跡 |
| `src/NativeImpl/LunaHook/LunaHost`・`include` | **Host、TextThread、API、IPCを一体として取得** | HOOKの生出力、コード、スレッド、PID、診断情報の取得 |
| ネイティブ共通ビルド資産 | **実際の依存を包含して取得** | version生成、文字コード判定、Unity補助、必要なDLLとヘルパー |
| `textio/textsource/texthook.py` と依存コード | **接続・探索・選択・保存・自動復元のロジックを積極的に流用** | 成熟した既存処理を再実装しない |
| `gui/selecthook.py` とHOOK操作に関わる部品、`LunaHost/GUI` | **Python Qt画面と既存C++ GUIの双方を再利用元として評価** | 探索条件、候補表示、履歴、手動HOOK、選択順、フィルタを既存動作に基づいて統合 |
| `myutils/config.py` 等のゲーム管理部分 | **ゲーム識別・設定復元方式を流用候補とする** | 自動接続とゲーム別HOOK保存 |
| `myutils/post.py` 等の取得品質処理 | **有用な補正・重複除去を流用候補とする** | 取得品質を下げず再実装費用を抑える |
| Lunaの翻訳・辞書・OCR以外の製品機能・別TTS・自動送り | **利用価値と重複を評価し、通常経路には二重実装しない** | AutoAdv本来の用途と競合させない |

Lunaのソースは可能な範囲で**元のまとまった機能群ごと**管理し、ゲーム別エンジン実装を手作業で選別・削除しない。対象機能の上流変更を反映するときに、対応ファイル追加を見落とす設計を採らない。ただし、移植元全ファイルの保存と、それらをすべて実行・ビルドすることは区別する。依存が重い場合、上流ソースを保持して必要な機能だけビルドする設計も比較する。

Python側は `gobject.base`、Luna固有設定・翻訳基盤、PyQt5/PyQt6の `qtsymbols` などに結合している。既存のネイティブ `LunaHost/GUI` も別のHOOK操作実装を持つため、移植前に双方が提供する機能と依存範囲を確認し、片方を見落として不要な再実装を行わない。**安易に互換wrapperを積み上げることも、機能ごとの全面再実装も既定方針にしない。** まず実際の依存を分類し、まとまった移植・元コードの局所的分離・AutoAdv統合層への接続のうち、上流追随の変更量が最も少ない方式を採用する。不要なLuna全体の実行環境を持ち込む必要が生じる場合は、採用範囲と費用を再評価する。今回は**LunaTranslator全体Forkではなく第2案**を実装方針とする。

## 3A. HOOK標準／OCR任意の改訂された完成時契約

AutoAdvはHOOKを**既定の本文取得源**とする。HOOKが利用できない、または品質が足りない作品でユーザーが明示的に選んだ場合のみOCRを使える。OCRを利用しない作品ではOCRエンジンや画像範囲校正は一切不要。音声同期・Utterance解析・TTS・入力判断は取得源と無関係な単一経路である。ゲーム画面の画像認識を一般的な進行制御の必須条件としない。

取得された本文は自動入力許可を意味しない。**候補原文 / 台詞確定根拠 / 発話提示完了 / 通常台詞の送り可能性 / 入力直前確認 / 入力後遷移ACK**をそれぞれ異なる事実として扱う。知り得ない事実をHOOK出力・OCR差分・無音・一定時間から捏造しない。

## 2. 先に確定する判断

1. **取得ポリシー**はゲームプロファイルに保存する。`hook`（新規プロファイルの既定）または`ocr`（ユーザーが選択）の二者択一とする。OCRの併用による自動突合・二重台詞生成・HOOK障害時の無断切替は**採用しない**。補完が必要なら証明可能な実例から再審査する。プロファイル切替でsource generationを変え、旧候補、ASR、TTS、タイマー、入力権限を無効化する。
2. **OCRエンジン**は初期実装で既にインストール済みのTesseract CLIと日本語学習データを使う任意Adapterとする。初期導入・モデルDL・インストールをAutoAdvが勝手に実施しない。パス、言語、OCR範囲はゲームプロファイルへ保存。失敗・文字化け・領域外・不安定更新はUNKNOWN。将来別エンジンへ交換可能な共通取得契約とする。Luna上流のOCR関連画像取得・範囲管理・更新処理は、依存全体を確認し利用価値のある部分を流用する。既存翻訳UI・OCR製品全体を常駐させない。
3. **取得結果共通契約**は原文と取得手段、ゲーム/プロファイルID、接続・取得世代、取得元（HOOKならPID・HOOK・thread/context、OCRならHWND・範囲）、単調時刻、受信順序、品質・状態を保持する。HOOKが送る`wchar_t`出力を生バイトと誤称しない。取得元を下流に渡す途中で捨てない。OCR文字列はHOOKと同じ確度・表示完了を自動的に獲得しない。
4. **台詞候補の安定**はTTS/ASR用の処理開始を判断する材料であり、ゲームへの自動入力可否とは別契約。部分更新、空出力、同文繰返し、複数HOOK、OCRのフレーム更新では、確定できない行境界を推定しない。
5. **自動入力の肯定的条件**は作品ごとの検証可能な実際の証拠に基づく。選択肢が存在しないこと、対象ウィンドウ・入力対象の一致、ゲームが通常送りを受け付けること、画面/操作状態の遷移確認などを判定する。画像テンプレートは**任意の証拠Providerの一つ**であり、標準必須にしない。入力可能を示す条件が欠ける場合も本文表示、HOOK設定、TTS試聴、音声監視は使用できるが、入力は停止する。`画面マーカーなし=安全`とはしない。
6. **遷移ACK**は入力操作後の独立した状態観測と同一セッション/世代の対応が確認できる場合だけ受理する。新しい本文、HOOK発火、OCR変更、経過時間単体はACKにならない。ACK前の再入力は禁止。タイムアウトは停止。
7. **音声同期**はnative Process Loopback＋VAD/ASR、選択的Irodori TTS、実再生完了、late native取消、silent閲覧時間を維持する。音声不明はnativeなしと扱わない。音声完了も送信許可ではない。
8. **手動選択肢**は明確な根拠が取れる作品だけ自動停止を検出する。手動介入で入力権限を失効させ、操作後の自動復帰にも新しい通常台詞・ゲーム状態・明示許可に相当する確認が必要。選択肢の不存在が判別できない作品は自動送り不可とする。
9. **UI**は取得方式・状態・原文・取得元・進行許可・不可理由を常時表示する。OCRがOFFでも情報を隠さず、範囲とエンジンは任意設定として表示する。画像校正操作を新規HOOKプロファイルの必須手順から排除する。作品単位の単一設定を正本にする。
10. 現段階では後方互換・テスト件数維持を目的にしない。既存の画面認識必須アサーション・設定スキーマとともに廃止・置換する。移行はユーザー操作による一回の読取り専用原本保全処理とし二重経路を残さない。

## 3. Domain間の接続と不変条件

`GameSession`が作品・プロファイル・実PID/HWNDと取得方式/世代を所有。HOOK/OCR adapterは観測を送るだけで、ゲーム入力も台詞境界の無根拠な確定もしない。Applicationは選択取得源だけをUtterance経路に渡し、同じ取得世代でない観測を拒絶。音声・入力・ゲーム状態の役割PIDが違う場合は根拠を持って結び、プロセスツリーやフォアグラウンドだけで確定させない。Controllerのみが入力を判断し、最新のゲーム肯定証拠と音声状態をInputGuardが入力直前に再取得する。

`取得源変更` / `ゲーム・プロファイル変更` / `Host切断・競合` / `OCR取得不能` / `対象PID・HWND変更` / `手動介入` で当該取得世代の未完了処理を破棄。イベントの遅配によって失効世代が復活しない。OCRの不確実な結果やHOOKの候補列挙だけでControllerに許可を与えない。

## 4. ネイティブビルド・起動・安全な接続

Windows上でx86/x64のHOOK DLLをビルドし、必要なHost DLL、DLL注入手段、補助資源を揃える。ビルドはMSVC/CMakeを基本とし、上流の現在の依存条件と成果物の対応を確認する。Lunaの `LunaHostDll.cpp` に公開される `Luna_Start`、`Luna_ConnectProcess`、`Luna_FindHooks`、`Luna_QueryThreadHistory`、`Luna_DetachProcess` 等の実際のABI、コールバック引数、型サイズ、寿命を、使用するソース版と一致させる。Python側 `ctypes` 定義とC++公開関数の引数個数・構造体レイアウトを静的・実行時の両方で検証する。具体的に、調査時点の `Luna_Start` は接続・切断・生成・削除・出力・診断・新HOOK・Embed・I18N・エミュレーター情報の**10コールバック**を引数に持つ。旧Python宣言を無批判に転記せず、採用版のエクスポートと照合し、callbackの生存期間・例外・文字列の所有権を確認する。

LunaのHostはターゲットが32bitか64bitかとは独立にホスト構成を持ち得るため、**Hostを機械的に対象ゲームと同bit数に固定しない**。既存のクロスbit注入手順、必要な補助プロセスを先に確認し、実際の成立条件から選択する。不要なLuna翻訳用Subprocess一式を別製品として常駐させることは避ける一方、既存注入ロジックを不用意に書き直さない。

**AutoAdv管理のHOOK HostをGUIとは別プロセスに置く構成を採用する。** 既存のネイティブ・ゲームDLL間プロトコルを保持し、AutoAdv本体との間で接続・切断・HOOK候補・復号済みテキスト・取得元・診断を転送する。Hostは第二の自動進行本体とせず、ゲーム入力・TTS・音声判断を行わない。Host障害のGUI/Controllerへの波及を防ぎ、イベントにHost起動世代とゲーム接続世代を付す。ゲーム内へ注入されたDLL自体の障害を別Hostで防げるわけではないため、対象ゲームの異常も監視する。IPCの途絶を正常な空台詞・音声不在と解釈しない。

上流のNamed Pipe・Mutex・DLL名は固定名を含むため、既存LunaTranslatorや別のHOOKホストとの同一対象ゲームへの同時接続を正常系として仮定しない。既存注入が検出された場合は勝手に上書き・Detach・killせず、競合を表示して対象接続を中断する。外部ゲームへ接続できない、権限不足、既存HOOK注入と競合、保護・アンチチート等により接続不能な場合は理由を示して中断する。保護機構を迂回する追加実装を成立条件にしない。AutoAdvが管理していないゲームプロセスや外部Lunaの終了・改変を行わない。Host障害やプロセス消滅はControllerの入力許可・進行中ジョブを確実に失効させる。

ビルド依存にはMinHook、uchardet、Lunaの補正処理、バージョン生成、Unity用補助DLL等が含まれる。`libuchardet.cmake` のcommit指定と `GIT_SHALLOW TRUE` の併用、`MinHook` の未固定ブランチ指定、Unity補助DLLコンパイラの固定パスは、取り込み時に再現可能なビルドへ整理する。上流CMakeにはブランチ名参照やビルド環境固有パスがあるため、採用版の依存をcommit/版/チェックサムで固定し、x86/x64のクリーンビルドで確認する。依存を固定するためだけにゲームエンジンソースを全面改造しない。

## 5. ゲーム識別・グローバル設定・複数プロファイル

AutoAdvを設定の単一の管理場所にする。

- **グローバル設定**：Irodori既存フォルダ・API、標準Voice、ASRモデルとtokens、Process Loopback環境、音声デバイス、保存先、ログ等の共通環境。ゲームごとに重複指定しない。対象ゲームへの入力許可・進行可能性の肯定的根拠は共通設定から暗黙継承しない。
- **ゲームレコード**：変更可能な表示名とは別の安定ID、既知のゲーム実行ファイル、必要なウィンドウ・起動条件、エミュレーター側ゲーム識別子（得られる場合）、使用履歴、既定プロファイルID。実行パス変更、ランチャー、エミュレーター、同名作品を考慮する。
- **複数プロファイル**：同一作品へ通常版・別HOOK・別設定を複数保存。各プロファイルに本文取得方式（HOOK既定／OCR明示選択）・HOOK選択・復元条件・OCR設定、取得補正、本文構造・読み置換、話者Voice、音声・画面・入力条件、必要な共通設定の上書きを一体保存する。プロファイル複製・改名・選択・削除をGUIで可能とする。
- **実行セッション**：現在のゲーム実体とそのプロセス群、HOOK取得対象PID、音声出力対象PID、画面・入力対象HWND、取得エンジン状態、実際に接続したHOOK、受信世代、フォーカス、音声監視、自動入力許可。PID/HWNDは再起動後に意味がないので永続プロファイルへ固定しない。

**複数プロセスを単一ゲームとして扱う契約を定める。** CEF等の描画子プロセス、音声出力を担当する別プロセス、エミュレーター本体と内部ゲームなどでは、HOOKを取得したPIDが音声捕捉や送り入力の対象とは限らない。ゲーム識別子に紐づけた実行中プロセス群を保持し、各観測・入力の対象を実際の根拠で割り当てる。ゲーム切替や役割PID変更は世代更新と再検査の対象にする。プロセスツリーの親子関係だけを対応確定の十分条件としない。

ゲーム自動識別にはプロセスパス・ウィンドウ・必要ならゲームエンジン／エミュレーターからのゲームIDを使用する。単にフォアグラウンドウィンドウになっただけでプロファイルを勝手に確定しない。同一実行ファイルに複数作品が対応する場合は識別根拠を明示し、不明なら選択させる。ゲームとHOOK元の対応はAutoAdvが直接管理した接続から確認し、Luna公開WSの文字列だけによる推測へ戻らない。

Luna内部の `savehook_new_data` や `gameuid` を活用することは認めるが、AutoAdvとLuna由来の設定ストアを別々に永続管理し、相互同期を必要とする構造は採らない。元のデータ形式を内部で再利用する場合も、GUI編集・実行・保存の正本を一つにする。既存AutoAdv設定と既存Luna設定の移行は原本を壊さない明示的な一回の処理とし、旧形式の二重実行経路を常設しない。特にLuna側の `savegamedata_5.3.1.json` にあるゲームUID、ゲームパス、選択HOOKとその順序、追加HOOKコード、ゲーム別取得補正を読取り専用で取り込み、AutoAdvゲームID／プロファイルIDへ関連付ける。Lunaの他バージョンや旧形式は実在する形式を確認して対応し、判定不能なゲーム・HOOKを勝手に同一視しない。既存Lunaデータへの書戻しをしない。ユーザーが全作品のHOOKを手動で再登録することを移行の標準手順としない。

## 6. HOOK探索・選択・復元・テキスト処理

Luna側の実用機能を具体的に継承する：ゲームエンジン自動検出、対象プロセス接続、HOOK列挙と実出力プレビュー、HOOKコードの手動追加、検索条件調整、文字コード／出力履歴、選択・解除、複数HOOKの優先順、保存HOOKの自動復元、取得品質の補正、エミュレーター固有対応。元機能の一部が現行のAutoAdv用途に不要なら、実際の使用価値で削除を判断する。便宜的な「最小実装」や代表作品限定版を完成とみなさない。

Hostからのイベントには、利用できる `process_id`、HOOKコード、thread/context、Host受信順序と単調時計時刻、Host／ゲーム接続世代、**TextThreadから通知された復号・バッファ処理済みの出力**を保持する。LunaHostの `OutputCallback` は既に `wchar_t*` の文字列を渡し、HOOK生バイト列そのものを渡すわけではない。ネイティブ側を変更して真の生データを取得することを、通常完成条件にしない。必要な診断上の利点が立証された場合だけ追加し、その場合も表示文・選択HOOK結合文・Utteranceの各段階と区別する。識別子と時刻の起点は実際のHostイベントで裏付ける。**HOOK出力1件を台詞1件、HOOK発火を画面表示完了とみなさない**。同文・部分更新・空出力・話者HOOKと本文HOOKの非同期・エミュレーター切替で根拠が欠ける場合は新しい台詞・進行許可を推定しない。

Lunaの選択HOOK復元アルゴリズム（HOOKコードやcontextの互換照合）を基礎にできるが、PIDや絶対アドレスを永続IDとして扱わない。更新・再起動後に候補が一致しない場合、誤ったHOOKを自動選択せずプレビューと再選択を促す。選択の成功は実際の出力と取得元の一致で確認する。上流の `match_compatibility` はcontextの下位16bit等を参照するため、単に互換照合が真になっただけで自動入力を許可しない。複数のHOOK候補が同じ条件へ一致した場合や、別プロセスから紛らわしい文字列を受信した場合は保留する。

複数HOOKの結合はLunaの選択順・短時間収集方式を再利用できるが、AutoAdvが取得元を直接保持できる利点も活かす。話者／本文を取得元別に扱う機能は、実例に基づき既存方式と比較する。近接時刻のみで話者を勝手に対応付けたり、前回話者を無根拠に補完したりしない。

テキストの標準処理順は「LunaHostの復号・バッファ出力 → 選択HOOKの取捨と必要な結合 → 取得品質補正 → Utteranceの話者・本文解釈 → TTS/ASRそれぞれの派生文」とする。結合や前処理の二重適用を防ぎ、Luna側とAutoAdv側に同じルールを複製しない。

`Utterance` は原文、話者、本文、TTS用文、ASR用文、読み置換、Voice・解析ルール版を共通保持し、GUIプレビュー・実行・音声照合で同じ処理を使用する。取得品質補正と発話解釈は同一設定画面で扱ってもよいが、同じ置換が二度かからないよう適用順を明確にする。`京(みやこ)`のルビ処理、`京`と`東京`の区別、引用符・改行・長文、未知話者、ナレーション、SKIP、読み辞書など既存の利便性を維持する。

## 7. GUIと通常運用

PySide6 GUIをAutoAdvの唯一の通常操作画面とする。Luna由来のHOOK選択GUIを広く流用することは許容するが、PyQt画面を別途起動してゲームを二重選択させることを完成形にはしない。PyQt5/6とPySide6、Luna独自のwidget/gobjectへの依存を実測・追跡し、元コードの利用、ロジックと表示の接続、UI部分の統合を総工数で選ぶ。使用するQt bindingをアプリ全体で一貫させ、GUIスレッドをHOOK探索・接続・再生処理でブロックしない。

常時表示する情報：現在のゲーム／プロファイル／PID・ウィンドウ、HOOK接続と選択状況、取得元と最新原文、現在Utterance、VoiceとIrodori、native/TTS/silent、取得方式・画面（採用時）・音声状態、進行許可、入力・ACK状態、停止理由。必要情報は無効時にも非表示にせず、位置を入れ替えず、無効理由を示す。原文の編集用プレビューと進行中の確定Utteranceは区別する。

初回の設定操作は、ゲーム選択→HOOK候補から選択・プレビュー→本文／話者・Voice・必要な画面条件を設定→作品プロファイルとして一括保存、で完結する。以後はAutoAdv起動時のIrodori自動起動、ゲーム検出、前回適切だったプロファイル・HOOK復元、観測開始を自動化する。通常の自動進行許可のみ利用者が明示的に行う。監視開始と入力許可を一つのイベントにしない。HOOK変更・ゲーム切替・プロファイル切替中には入力を禁止する。選択肢操作後の自動復帰は元の安全契約を維持する。

画面の画像テンプレート照合は、ゲームごとに肯定的進行条件・禁止条件を確実に証明できるときだけ採用する**任意の観測手段**とする。一般的なHOOKプロファイルで画像マーカー・画面校正を必須としない。画像を使用する場合はAutoAdv内でゲーム画面取得・範囲指定・閾値・プレビュー・保存が完結する。画面が取得できないことや認識対象が存在しないことを「安全に進行できる」と読み替えない。入力可能の肯定的根拠が欠ける作品では原文プレビュー、音声同期・試聴等は利用できても自動入力は停止する。

## 8. 音声同期・Controllerとの統合

HOOK取得源の変更は、既存の音声同期機能を再実装する理由にならない。ネイティブゲーム音声のProcess Loopback、VAD・ASRのUtteranceとの帰属、TTSの合成と実再生完了の区別、遅れて開始したnative音声によるTTS取消、無音閲覧時間、IrodoriのVoice取得と起動、選択肢画面での入力停止・手動操作後の安全な復帰を継続する。Irodoriが稼働していないことだけで、HOOKや原文プレビューなど無関係の操作を停止しない。

Controllerだけが自動入力を判断する。ゲーム実体とHOOK/音声/画面/入力の対象PID・HWNDの対応を現在セッションで照合する。音声捕捉の失敗、別プロセスへの出力、取得元不一致は「native音声なし」ではなく不明扱いにする。接続・ゲーム・プロファイル・HOOK・観測対象の変更による世代更新時に、古いUtterance／ASR／TTS／タイマー／送り要求を失効する。入力直前に対象ウィンドウとPID、フォーカス、その作品で検証済みの入力可能性の肯定的証拠、音声条件、手動介入、送信済み・ACKを再検査する。**1行1入力以下、ACK前の再送禁止、根拠不明時の停止**を維持する。Luna由来の自動送り・翻訳TTS・ゲーム本来のAutoを並列の入力主体にしない。

## 9. 上流更新・改変管理

Luna上流全体の特定commitを基準に取り込み、HOOK関連の一貫したソース・資源・ビルド依存を保存する。取り込み用の再現可能な手順を用意し、上流コミット、採用範囲、外部依存版、取込み差分、パッチを記録する。AutoAdv固有変更は原則として外側の統合コードやビルド定義に置き、上流ソースへの改変が必要なら最小限の独立差分として追跡する。これは**移植する機能を最小化する制約ではない**。

更新手順は「前回採用コミットと候補コミットの差分を取得 → 追加・改変されたゲーム対応、Host API、IPC、設定・GUI関連処理を確認 → 関連ソース一式を更新 → Windowsビルド・契約テスト・回帰テスト → 採用」である。上流でPython側のHOOK復元・ゲーム管理が変更された場合も確認対象に含め、C++だけを更新して完了としない。新しいソース・依存の未検証自動採用や、アプリ起動時の上流ソース更新は行わない。

取り込み結果に未解消のABI不一致、既存プロファイル破損、既知の誤HOOK接続があれば次版を採用しない。上流ソースに翻訳埋込み・ゲーム表示改変・フォント変更等のコードが存在しても、AutoAdvの通常取得動作で不要なら呼び出さない。ゲームエンジンのHOOK取得に必要な副作用については機能ごとに実際の必要性を確認する。ソースを広く取り込むことと、無関係なゲーム改変を標準で有効にすることを混同しない。上流追随を容易にするために成立済みlocal commitのreset/rebase、特殊ブランチの常設、既存publish経路の改変は行わない。

## 10. 個人利用・ライセンス・公開リポジトリ

本ソフトは**個人利用専用**であり、商用販売、第三者向けインストーラ、サービス提供、多人数運用、販売・配布支援を完成条件に含めない。これは上流ソースを狭く採用する理由にはならない。

一方、現在の `naro0216n-collab/AutoAdv` は公開リポジトリである。GPLv3のLuna由来ソースを公開リポジトリへcommitする場合は、利用者が一人であることと区別して、適用ライセンス、原著作者表示、改変表示、必要な対応ソース・ビルド手順、第三者ライブラリと資源の権利を整理してから公開する。別プロセスに分離しただけでGPLの適用がなくなると仮定しない。個人使用のためのローカル改変を必ず公開する必要がある、とも誤解しない。法的判断に不明点があれば根拠と公開範囲を示す。個人利用の目的を勝手に変えたり、著作権保護のためだけにLuna再実装へ戻したりしない。

## 11. 実装の順序とcheckpoint

1. **正準の改訂**：既存仕様のLuna公開WS前提・Luna外部設定を解消し、本指示書の目的と保存・実行契約に揃える。既存テストの意味を再評価する。
2. **上流採用範囲の確定と取込み**：固定上流commit、ネイティブ一式・共通依存・Python HOOK機能を取得。採用範囲・ライセンスを整理し、上流追随の手順を整備する。
3. **Windowsビルドの成立**：x86/x64のHook、必要なHost・注入・補助資源をクリーンビルドし、実際のABIとプロセス・HOOKイベントを検証する。ビルドのみを実ゲームHOOK成立とは扱わない。
4. **HOOK操作・プロファイルの統合**：ゲーム識別、探索、候補プレビュー、手動追加、選択順、復元、取得品質、ゲーム／複数プロファイル／共通設定を一体化する。旧設定と二重保存しない。
5. **Utteranceと実ゲーム監視を縦断接続**：取得元・世代・ゲームを構成するプロセス群、音声／画面／入力の対象をApplicationに渡し、Controllerによる安全な進行を成立させる。
6. **GUI通常経路の統合と旧経路撤去**：作品管理・HOOK・任意OCR・Voice・監視・許可をAutoAdvで操作可能にし、新経路が成立したら公開Luna WS前提のRuntime、LunaWorker、二重監視、旧設定・不要なCLI/説明/テストを整理する。診断入口を残す場合も第二の自動送りループは作らない。
7. **Windows実ゲーム検証・運用整備**：異なるエンジン、32/64bit、話者／本文の別HOOK、再起動・ゲーム切替・選択肢・音声あり／なし等を確認し、実機未検証を明示する。

上流の大量ソース・リソースを取り込むcheckpointでは、実際のPublish Gateway transportの容量・操作数制約を正規helperで事前把握し、必要に応じて自然な機能境界で取込みcommitを分ける。正規手順を変更する、成立済みcommitを作り直す、`temp`等で中継することで回避しない。Windows用CIは既存workflowが通常Gateway publishのたびに起動するとは限らず、現行 `windows-adapters.yml` のpaths条件には新規Luna移植ソース領域も含まれていない。ネイティブ関連checkpointでは対象ソースを対象に含むCI構成と**実際に発火する実行経路**を確立し、そのcommitのrun結果を確認する。`workflow_dispatch` や `workflow_run` が利用可能とは、default branch等のGitHub Actions側条件を確認する前に仮定しない。`main`の承認条件を破り、通常publish以外の開発中継で強引に実行することは避ける。Fast CIだけでネイティブ成立を宣言しない。

各checkpointは「一つの責務がApplicationまで成立した」「関連テストが通った」「旧経路を撤去できた」等の自然な区切りでcommit・`develop`へpublishする。全体完成を待たない一方、動作しない断片やテスト未実施の微修正を無条件にpublishしない。

環境は最新の `develop` Fast CI `source-snapshot` から復元し、`scripts/publish_request.py init` を実行する。通常はローカル実装→関連検証→commit→`publish_request.py prepare`→publish直前のremote `develop`/`publish` HEAD取得→helperの `connector-plan` と固定Launcher出力を**変更せず実行**→Gateway成功後 `record`→次のpublish前に前回Fast CI確認、という標準経路を使用する。`main` は明示承認まで更新せず、versionも承認なしに変更しない。`temp`・追加worktree・他の開発ブランチを通常開発の中継に使用しない。標準Gatewayが失敗した場合は規定文書へ戻り、独自経路で回避しない。

## 12. テスト・受入条件

| 領域 | 成立を確認すること |
|---|---|
| ビルド | x86/x64・必要なHost/Helper/資源のクリーンビルド、版・依存固定、実装ABI・callback署名の一致 |
| ソース追随 | 上流でゲーム対応・Python側HOOK管理が変更された場合にも追加・更新を検出でき、実コードへ取り込める |
| HOOK接続 | 対象PIDへの接続と安全な切断、実ゲームのHOOK候補・復号済み取得文・Hook/thread/contextの取得。真の生バイト列の取得とは区別 |
| ゲーム管理 | 複数ゲーム、自動識別、同名ゲーム、パス移動、エミュレーターでの対象切替、HOOK・音声・画面・入力PID/HWNDが異なるゲーム構成に対応。未知は誤確定しない |
| プロファイル | 一ゲーム複数プロファイル、保存・複製・切替・復元、一括保存、グローバル設定再利用、既存AutoAdvおよびLunaのゲーム・選択HOOK設定からの読取り専用移行 |
| HOOK利用 | 自動検出、選択・順序・複数HOOK・手動コード、部分更新、再起動後の復元、候補不一致時の停止 |
| 本文 | 話者／本文／読み・ルビ／Voice割当てとUtteranceのGUI・ASR・TTS・実行結果の一致 |
| 進行 | native／TTS／silent、late native、選択肢で停止→手動選択後の条件付き自動復帰、異常時停止、1行1入力・ACK待ち |
| 切替・異常 | ゲーム・HOOK・プロファイル変更、Host異常、対象プロセス終了時に旧ジョブ・入力許可が確実に失効 |
| GUI | Lunaを別途起動・設定せずHOOKから音声・監視まで操作可能。ゲーム画面の校正画像取得・領域選択・結果確認もAutoAdv内で完結し、重要情報を常時表示し、GUIが固まらない |
| 旧経路 | 新経路成立後、Luna公開WSの並列監視、Luna側への設定操作、二重状態・二重設定、旧仕様専用テストが残らない |

Unit/architecture/integrationはState所有、観測イベントと世代、プロファイル一貫性、入力抑止を優先する。Windows CIでは実際のネイティブビルドとWin32 GUI・Hostの起動/接続を確認する。可能ならテスト用の無害なWindowsプログラムを対象としてHostからのイベント・デタッチ・異常停止を再現し、単なるモック呼出しの成功でネイティブ接続を代替しない。ただしテスト対象プログラムを実ゲームの互換性の証明に使わない。Windows実機では別エンジン・別bit数の実ゲームを用い、選択したHOOKが正しく届き、native/TTSが同期し、選択肢から復帰し、連続進行中に誤送りしないことを観測する。CI greenや模擬HOOKだけでは実ゲーム成立を宣言しない。実ゲーム未検証箇所は未達として報告する。

## 13. 完了判定と禁止する誤った代替

完成と判断できるのは、AutoAdvだけでゲームとHOOKを選択・保存・復元でき、既存Lunaの広いゲーム対応資産が利用でき、ゲーム別・複数プロファイルがIrodori・Utterance・Controllerへ接続し、実ゲームで音声同期・入力の安全性が確認できたときである。個人利用に不要な配布製品化は完成条件に含めない。

次の振舞いは要求達成と見なさない：C++のごく一部のみ取り込みゲーム対応を縮小する、Python側HOOK管理を根拠なく全面再実装する、Lunaの独立GUIを日常必須操作として残す、データを別々の設定ストアに保持して手動同期させる、HOOK受信だけで台詞確定や自動送りを許可する、旧公開WS経路を正常運転の並列経路として残す、UIの都合で重要情報を隠す、未検証の上流更新を自動適用する、既存テストの成立を目的として旧仕様を保持する。
