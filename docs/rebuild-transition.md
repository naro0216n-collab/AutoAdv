# AutoAdv ゼロベース再構築・サルベージ移行計画

本書は`docs/integration-spec.md`の完成条件を実装するための**移行用作業文書**であり、製品仕様や旧実装を正当化する文書ではない。2026年10月20日時点の`develop`（開始基点：`436fd188150e90cc4ed3afc97a81bdb595abda83`）を調査の起点とする。作業開始時には最新`develop`と正準文書を確認する。

## 1. 再構築の選択

**設計をゼロベース、実装の再利用を実利基準、検証を実ゲームの動作基準**とする。旧コード・旧テスト・旧状態遷移を全件解析して妥当性を証明することを着手条件にしない。逆に、モジュールが古いという理由だけで安定したHOOK・音声・TTS・設定の実装を捨てて再実装もしない。

変更対象の中心は、HOOK取得、Utterance、音声・TTS、会話送りが切れ目なくつながる**単一の実行経路**である。継続利用する外部技術の契約だけを必要十分に調査し、状態所有と処理順序を新設計から確定させる。GUIと永続設定まで縦断して接続する。成立済みの責務の二重実装を放置しない。

対象外機能の存在や副次的な成立を理由とする積極的な削除・不成立の保証はしない。不要な機能が中核の実装・操作・設定・保守を実際に妨げているときに、因果関係を示して整理する。旧テストの合格、件数、既存モジュールの利用率を成果指標にしない。

## 2. 再構築に先立って確定する契約

ここで述べるのは必要な責務であり、旧クラス名・旧パッケージ境界をそのまま採用する指示ではない。

| 責務 | 入出力・所有する事実 | 責務外 |
|---|---|---|
| GameSession | 現在の作品・プロファイル、取得元の選択と世代、実際のHOOK/音声/入力対象の対応、許可の失効 | ゲーム全状態の探索・分類 |
| Text Acquisition | 選択HOOK（任意OCR）の出自付き観測、候補・更新、探索・選択・復元 | 台詞ごとの音声判断やゲーム入力 |
| Utterance | 原文から話者・本文・読み・ASR/TTS派生文・Voiceポリシーを一貫生成 | 独自の録音・入力・別設定の保存 |
| Audio/Presentation | 対象ゲームの既存音声の照合・再生完了、TTS生成と実再生・取消、閲覧時間 | 入力権限やゲーム場面全体の認識 |
| Conversation Advancement | 明示許可、現在台詞の提示終了、一度だけ入力、次の候補待ち、手動停止と失効 | 全選択肢の識別・自動選択・汎用ゲーム操作 |
| Preferences/GUI | 単一正本で保存・復元、利用者に必要な操作と状態・停止理由を一貫提供 | もう一つのController、外部Lunaとの二重設定 |

最初の着手判断として、(a) 台詞候補と台詞境界をどの証拠で区別できるか、(b) native/TTS/無音の分岐と曖昧さをどう設定するか、(c) 入力後の新候補を同文反復を含めどう扱うか、(d) 手動停止・再許可をどう成立させるかを具体的な使用場面で確定する。未知をすべて観測する仕組みは作らない。実例で確認できない機能は既知の制限として扱う。

## 3. サルベージ候補の一次仕分け

下表は**調査の優先順位**であり、ファイルの残存・削除の確定表ではない。必要な実行契約が成立すれば同一モジュールをそのまま採用してよい。複数ファイルにまたがる一責務は一括で判断する。

| 既存の主要コード・資産 | 初期方針 | 採用前に確認すること |
|---|---|---|
| `scripts/sync_luna_upstream.py`、Luna Native一式、ビルド関連 | 積極的サルベージ | pinned版の範囲・ライセンス・上流差分・x86/x64再現ビルド・ゲーム対応範囲 |
| `luna_abi.py`、`hook_host.py`、`hook_host_worker.py`、`hook_protocol.py` | サルベージ優先 | 実ABI・コールバック寿命、IPC途絶、HOOK候補・出自・Host世代と実接続 |
| `hook_application.py`、HOOK選択・復元処理 | 必要な機能を採用・組直し | 単一/複数HOOK、手動追加、出力品質、保存HOOK復元、誤接続の抑制 |
| `acquisition.py`、`ocr.py`、`screen.py` | 契約を揃えて部分採用 | 標準HOOKの依存なし、OCR明示選択時だけ画像・Tesseract、出自と世代 |
| `text.py` | サルベージ優先 | 本文構造、読み替え、ルビ、話者別Voice、ASR・TTSとプレビュー一致 |
| `irodori.py`、`irodori_server.py` | サルベージ優先 | 既存サーバー検出・自動起動、Voice取得、TTSの実再生終了と取消 |
| `process_audio.py`、`audio_buffer.py`、`audio_match.py`、`audio_recognition.py`、`native_gate.py` | 技術処理をサルベージ、判定契約は再評価 | BGM・効果音・native遅発・無音台詞、ASR不使用モード、音声対象の妥当性 |
| `contracts.py`、`controller.py`、`application.py`、`runtime.py`、`live.py`、`live_guard.py`、`windows_input.py` | **実行モデルから再構築** | 旧イベント・タイマー・許可状態を持ち込まない。台詞に対する単一進行権限、入力前再検査、次候補を含め実動作で確認 |
| `profiles.py`、`preferences.py`、`services.py` | 保存資産を部分採用 | 作品/プロファイルの一元性、共通音声設定、ユーザー資産の安全な移行・自動復元 |
| `gui.py` | 有用なUI部品をサルベージして再編 | 日常操作、表示と実状態一致、HOOK探索・Voice割当て・監視・許可の一体性、操作負担 |
| `evaluation.py`、`__main__.py`、補助診断 | 利用価値で判断 | 実障害の調査に有用か、第二の処理本体・独立した設定正本にならないか |

既存コードを捨てる範囲を先に一律決定しない。必要な関数・データ処理だけをサルベージする場合もある。移植済みLunaの資産を再実装するなら、元実装を使わないことによる初期・将来の費用を比較し、具体的な利益を示す。

## 4. 移行前に明らかにする現状の不足

以下は移行候補を調べるための出発点であり、正準仕様へ転記する禁止項目ではない。

- `run_windows()`の取得・音声・入力対象が単一PID/HWNDに寄っている。必要な作品では役割の対応を明確にし、汎用的なプロセス網羅監視にはしない。
- 現状はGUIからの明示許可がすでに台詞処理中の場合に通らない可能性がある。利用者が原文を確認して許可する通常操作から再設計する。
- 音声の存在を確定できない場合にTTSが始まらない／停止する条件があり、BGMと音声の混在作品やTTS専用運用で実用性を検証する必要がある。
- 選択HOOKの保存と実際の取得品質・複数HOOK利用、作品自動認識、設定復元には分断がある。既存のLuna処理を利用できるか先に確認する。
- 手動介入・入力後の新候補処理、同文の別台詞に関して、実経路と単体テストにギャップがある。台詞境界の推定を都合よく簡略化しない。
- GUIと旧スキーマは実行時に必要な設定・表示と一致しない箇所がある。複製保存や同じ意味の複数入力を避ける。

この一覧を完全に確認することを作業着手のゲートにしない。再構築した中核経路で問題が解消される場合、旧経路の詳細な因果解明を不要とする。

## 5. 再構築と移行の実施順序

### checkpoint A：製品仕様と実行契約

正準文書から具体的なユーザー操作・入力事実・状態の所有者を定義する。提示すべき最小の状態は、選択台詞、原音照合、TTSまたは閲覧、入力許可、送出済み、新候補待ち、停止理由である。これらが**一つの処理順**で成立する設計を作る。旧Controllerのenum数やevent一覧を移植目標にしない。

検証可能な代表的な連続会話のイベント列を定義する。再現用fixtureは実装代用品ではない。インターフェースの責務が成立し、テスト方針が正準仕様に一致したところでcheckpointを切れる。

### checkpoint B：HOOK→Utterance→GUI

実HOOKの探索・選択・復元と候補出自を、一つのGameSessionからUtteranceとGUIへ通す。話者・読み・Voice設定の保存・再読み込みまで縦断して完成させる。複数HOOKは作品で必要な場合に対応を判断し、無意味な推定結合を増やさない。別途Luna設定を日常操作に要求する構造を残さない。実行が成立した新経路に対応する旧経路を撤去する。

### checkpoint C：Utterance→音声→選択的TTS

Process Loopback・VAD/ASRとIrodori資産を接続する。原音あり、原音なし、同一作品内で混在、BGMあり、遅れて始まる原音、TTS失敗、音声監視なしのTTS専用を一続きの会話として検証する。原音の完全な不存在証明やゲームの全面監視を目標としない。未解決の場合の保留・設定・停止条件を利用者の目的から決める。

### checkpoint D：単一会話送り経路

音声または閲覧の終了後に、明示許可、対象・フォーカス・手動介入・未送出を直前検査して入力する。新しい候補・繰返し・部分更新・セッション切替の扱いを接続し、連打・早送り・旧イベント復活を防ぐ。選択肢の完全検出・独立画面ACKなどを中核に再導入しない。入力条件が不明なときも取得や読み上げを止める必要があるか個別に判断する。

### checkpoint E：通常操作・設定・実ゲーム

複数作品・プロファイルの自動復元、必要な音声依存だけの設定、Irodori起動、Voice割当て、監視・試聴・停止・再開をGUIで確認する。Windows x86/x64 Native、異なるゲームエンジン、音声有無、同文・部分更新、手動介入を実ゲームで検証する。未検証の範囲は明示する。実運用に関係ない範囲を無制限に広げない。

これらは責務と検証のcheckpointであり、全段階を完了するまでcommit/publishしないという意味ではない。各段階の内部でも自然なまとまりを検証したら保存・publishしてよい。旧新の二重実行経路は暫定的に維持せず、単一経路の成立にあわせて置換・撤去する。

## 6. 既存ユーザーデータの扱い

再構築はユーザーの設定資産を破壊する許可ではない。現在のAutoAdv設定と既存Luna設定を、**原本保全・読み取り専用取込み・明示承認・一回の一方向変換**で新しい設定正本へ移す。新旧設定へ日常的に同時書込みしない。設定スキーマを現在のものと同じに保つことは目的ではない。

取込み対象は安定した作品識別、ゲームパス、プロファイル、HOOKコード・選択順・手動追加、取得補正、本文分離・読み、話者Voice、Irodori接続など、実際に利用できる情報を優先する。旧画面状態認識・選択肢判定等が保存されていても、新たな中核設定と偽って読まない。原本に保持されていれば、これらを新システムで積極的に破壊する必要はない。

原本の存在・ハッシュとバックアップ、対応形式、変換項目、未移行情報、失敗時の非変更を検証する。形式を識別できない場合は勝手に初期化せず、ユーザーへ提示する。複数回インポートによる重複作成を防ぐ。自動移行は明示承認なしに実行しない。

## 7. テストの移行基準

旧テストの名前・件数を引き継がず、**正準仕様で意味のある観測可能な結果**から契約を作成する。

1. HOOK選択の出自・世代・復元、同文や部分更新を含むUtterance確定。
2. 話者・本文・読み・Voiceの一貫性、無声台詞のTTS、原音優先、遅発原音時の取消と再生完了。
3. ユーザー許可の操作性、進行の1台詞1入力、手動停止、接続失効、前台詞の再送・再生防止。
4. プロファイル・設定の保存と復元、GUIからの実操作、旧データの安全な取込み。
5. Windows実機のNative Host・音声・入力の結合。ゲーム固有の成立は実ゲームで区別して確認する。

既存のユニットテストは、上の検証に**実質的な意味がある**場合に限り変更なし採用・書換え・統合する。旧仕様の維持のためだけのassertionや実装は削除する。テストが失敗した場合は、assertionの必要性・契約の正しさ・重複を先に確認する。テストを通すためだけにProductionコードを曲げない。

選択肢の自動選択、ゲーム状態の完全観測、対象外機能が成立しないことなどの**非要件をアサーションにしない**。逆に中核への実際の悪影響がない任意機能の存在を検出して落とすテストも作らない。

## 8. 作業・公開手順と判定

ローカルでの作業は`docs/publish.md`に従う。既に最新`develop`のsource-snapshotから復元された有効なローカルrepoがあるなら継続利用する。必要なら最新Fast CIの`source-snapshot`から復元し、`scripts/publish_request.py init`とrepo-local identityを整える。復元失敗を通常のcloneなどに読み替えない。通常開発に追加branch・worktree・`temp`中継を導入しない。

検証済みの自然なcheckpointでcommit→`publish_request.py prepare`→remote `develop`/`publish` HEAD取得→helperが生成する順序そのままのGateway操作→成功後`record`。次のpublish直前に前回Fast CIを確認する。成功したローカルcommitをpublishのためにreset/rebaseして作り直さない。`main`・versionは承認まで更新しない。

各checkpointの報告は、**実際に利用できるもの、再利用した資産、整理した重複経路、実行した検証、残る未成立・未検証事項**に限定する。旧ファイルを何個消したか、テスト件数を何件保ったか、任意機能をいくつ不可能にしたかを成功基準にしない。
